# Relay agent activity monitor

Feature `wi_c738cdd5f9ef637b` revision 1, owner order #10744, builder assignment #11046 and exact Start #11056 (handler verification #11059).

The launch-host relay observes only its exact Codex or Claude session file. Codex bindings use the recorded thread UUID; new Claude launches bind the stable session UUID chosen by `tt spawn`. Transcript offsets, partial lines, tool-call signatures and worktree fingerprints remain in private files under `TAILTERM_RELAY_STATE` (or `~/.local/state/tailterm/relay`). A pass reads at most 4 MiB of appended bytes; a record is limited to 1 MiB. Truncation or rotation resets parser state. The hub receives a typed activity state, event times, a bounded tool name and cumulative token totals. It never receives transcript lines, tool arguments, or worktree content.

The Codex parser accepts turn boundaries as `event_msg` payload types and the older top-level shape. It pairs `function_call` arguments and `custom_tool_call` input with their call IDs. Claude parsing accepts assistant tool use, user tool results and per-message usage. A Claude turn completes at an assistant `end_turn`, a `result` record, a `system` `turn_duration` record, or Claude Code's API-error record (`isApiErrorMessage`, model `<synthetic>`, `stop_reason` `stop_sequence`); the last two also clear pending tool calls. After an API-error turn, `idle` and `finished_silent` carry the reason `turn ended by API error (<code>)`, where the code is Claude Code's `error` value only when it matches `^[a-z_]{1,40}$` (bug `wi_132c8895adfe0886`, order #15557); no other transcript text is sent. A normal turn end leaves the reason empty. The relay reports a reason only with a state or wake change, so a second API-error turn between two idle reports is not re-sent. A new user text record clears the completed-turn state and the reason; a tool result does not. A malformed, oversized or future record is skipped within the bounded read; usable later records recover the state. Before a recognizable turn, the state is `unknown`. A Claude binding that fails at spawn is retried by the host relay against a locally verified tmux session and the exact hub run. Relative or missing Claude working directories omit worktree loop detection rather than probing a different tree.

Defaults selected by the owner in #11040–#11042 are a 120-second working window, a 10-minute hung-tool threshold extended by a longer explicit wait, five identical completed calls with token growth across five minutes and no worktree change for looping, and two confirmed missing-runtime probes at least 15 seconds apart for crashed. `TAILTERM_ACTIVITY_WORKING_SECONDS`, `TAILTERM_ACTIVITY_HUNG_SECONDS`, `TAILTERM_ACTIVITY_LOOP_SECONDS`, `TAILTERM_ACTIVITY_LOOP_CALLS`, and `TAILTERM_ACTIVITY_CRASH_PROBE_SECONDS` override those bounds. Probe errors and unknown transcript formats yield `unknown`. Planned `needs_input` waits do not trigger hung or crash classification. Detection only notifies; it never nudges, resumes, interrupts or restarts an agent.

The relay polls activity after inbox and broker delivery and uses the existing host request budget. It checks hub eligibility before local transcript and worktree scans, caches each worktree probe per pass, and runs Git with optional locks disabled. It saves a pending transition and stable request identity before HTTP; a lost reply replays the same report no more than once per 15 seconds. A permanent 409 rejects that snapshot without claiming it committed or retrying it forever; a later state or wake-outcome change can be reported with a new request identity. The hub stores one snapshot per exact agent run and an immutable retry receipt. A steady state and steady wake outcome, including token growth, creates no hub write; changed wake outcomes persist even when activity remains idle. Agent and team usage are last-transition snapshots, not live counters. Team totals are derived from persisted exact-run snapshots linked to the work item, including closed runs. A shared worktree fingerprint can show change, but cannot identify which agent edited it. The wrapper records its exact agent/run, tmux session creation identity, child PID and process creation identity in a private host-local receipt; it marks the receipt when the child exits. A confirmed missing tmux session, exact wrapper exit receipt, or missing exact PID starts the two-probe crash check. A reused PID or session, absent identity, permission error, or ambiguous probe yields `unknown`. A hub heartbeat gap alone cannot confirm a local crash.

Projects shows the activity state beside lifecycle and the last-transition usage and evidence age in agent details. Claude wake outcome, pending message sequences and a bounded skip/failure reason appear alongside that state. `tt agents` shows activity plus the same usage snapshot. `tt relay --status` shows its local wake outcome. Delivery and `tt team queue list` show each member's state and team totals. On a transition to `hung_tool`, `crashed` or `looping`, the hub sends one typed notice to that item's current lead. A crash also posts an owner-facing notice; a lead's hung-tool or looping transition posts one owner-facing notice. No team outside the item's own lead mapping receives a directed alert.

A live agent that cannot make progress reports `stuck` with a bounded reason (bug `wi_b6b79229c8fec99d`, order #14836). This happens in two cases. The first is a pane below 80x24, read from the session's agent window, for any runtime: `pane 16x1 below minimum 80x24`. The second is a Claude wake that has stayed `uncertain` or `exhausted` for three minutes since its first attempt, while the agent is idle, finished silently or unknown, and still has unread input: `Claude wake unconfirmed for 4m (retry 2/4): retry 2/4: Enter on own unsubmitted text`. `TAILTERM_ACTIVITY_WAKE_STUCK_SECONDS` overrides the three minutes. A working agent is never stuck from its wake record, and `runtime_prompt` takes precedence. Projects shows `Stuck: <reason>`. Agent windows start at manual 200x50; an eligible focused TailOS pane can size them while preserving at least 80x24 usable program dimensions (bug `wi_9e5d8194ed093cd4`, order #24075), and the relay's bounded wake retry is in [claude-wake.md](claude-wake.md). A hub from before this state answers HTTP 400. The relay then reports `unknown` with reason `stuck: <reason>` under a new request identity and remembers the downgrade for that run, so later transitions still post. `stuck` sends no directed alert.

A quiet live runtime that is waiting on its own modal prompt (a Codex menu or a Claude dialog) reports `runtime_prompt` with a typed prompt kind, even while the agent's status is `needs_input`; the status itself is never changed. The prompt policy, answers and once-only escalation are in [runtime-prompts.md](runtime-prompts.md).

An agent whose provider refuses its requests reports `provider_blocked` with the provider, model, error class and first-seen time (bug `wi_72f41bd375032cf0`, order #11854): a usage or credit limit, a 401 or 403, or repeated 429 or 5xx failures, read from typed fields of the Codex or Claude transcript. No provider text reaches the hub. The item lead is told once per episode and the owner once after a short grace period, or once per runtime when every active agent of it is blocked. Detection, the notification rules and the recovery action per class are in [provider-blocked.md](provider-blocked.md).

An agent's activity also carries `matrixWait` while the agent has a live verification run in its host's matrix lock (bug `wi_772e88d71e5cd0e5`, order #21150). On each activity check the relay reads the lock file that `scripts/verify-matrix-host-lock.mjs` keeps (`TAILTERM_MATRIX_HOST_LOCK` when it is an absolute path, else `~/.local/state/tailterm-matrix/host.json`; see [objective-verification.md](objective-verification.md), "Host lock and waitlist"). An entry belongs to the agent when it names the agent (the run's `TAILTERM_AGENT_NAME`), its process is alive, and its item, when the entry names one and the agent is bound to one, is the agent's item. The field is added beside the transcript state, which does not change: a lead whose detached matrix run waits is still `idle`. It holds `role` (`waiting` in the waitlist, `running` while holding the host), the run's `item`, `position` and `length` among the waiters, and `since` (when the run asked for the host, or when it got it). No pid, commit, path or output of the run is sent. A wait that appears, changes role or ends is a new report; a moved position is not. An absent, unreadable, malformed, other-version or other-host lock file sends no field and no error. An older hub ignores the field.

**Recording a planned wait so the queue does not call the team idle.** The team queue's `idle-entry` stall ([team-launch.md](team-launch.md)) fires when every live member of a running entry is idle or done with no open work for the idle threshold. Each of these counts as open work:

- A matrix run in the host lock, waiting or running. This is automatic through `matrixWait` when the run is started through `verify-matrix.mjs` or the lock's `exec` with the agent's `TAILTERM_AGENT_NAME` set; nothing has to be posted.
- An unanswered owner decision posted with `tt ask`. The answer restarts the idle time.
- An open obligation the team holds or sent: an ASSIGN, REQUEST, REVIEW or QUESTION that is not closed, including one answered with a typed BLOCK (`--resume-when`), or a BLOCK sent to the project orchestrator.
- A member whose status is `needs_input` (`tt event needs_input --text "waiting for …"`), for example while a dependency lands on the branch. Its activity is `unknown`, not idle.

A reported matrix wait stops counting 4 hours 30 minutes after its `since` (the lock's wait limit is 240 minutes and its holder limit 122 minutes; `since` restarts when the run gets the host). On the host it ends sooner: the relay drops the field on its next 15-second check once the run exits or leaves the lock file, and the idle time then starts from that report. The bound matters only when the relay itself has stopped reporting. An open owner decision has no such bound; the broker's owner escalation covers it. Limitations: a run whose lock entry names no agent (`agent: unknown`) and a wait kept outside the lock (a shell loop that watches processes) are not seen; a reused pid can keep a dead entry counted until the lock removes it or the bound passes; and a waiting team is named by its member's `matrixWait` in the agent and queue JSON, not by a notice.

Synthetic checks are `go test ./cmd/tt -run 'TestActivity|TestMatrixWait'`, `go test ./internal/store -run 'TestActivity|TestProviderBlock|TestQueueStall'`, `go test ./internal/broker -run TestBrokerProviderBlockSweep`, `node tests/activity-browser.mjs`, `go vet ./...`, `go test ./...`, and `npm test`. Browser checks use disposable Chromium and WebKit contexts; default Go checks use synthetic transcripts, fake process/tmux probes and isolated SQLite/HTTP fixtures. The opt-in Claude wake check reads only its own disposable session transcript on a private tmux socket and local test hub. No check touches the live hub, relay, a working agent's transcript or the host's live matrix lock file.
