# Relay agent activity monitor

Feature `wi_c738cdd5f9ef637b` revision 1, owner order #10744, builder assignment #11046 and exact Start #11056 (handler verification #11059).

The launch-host relay observes only its exact Codex or Claude session file. Codex bindings use the recorded thread UUID; new Claude launches bind the stable session UUID chosen by `tt spawn`. Transcript offsets, partial lines, tool-call signatures and worktree fingerprints remain in private files under `TAILTERM_RELAY_STATE` (or `~/.local/state/tailterm/relay`). A pass reads at most 4 MiB of appended bytes; a record is limited to 1 MiB. Truncation or rotation resets parser state. The hub receives a typed activity state, event times, a bounded tool name and cumulative token totals. It never receives transcript lines, tool arguments, or worktree content.

Defaults selected by the owner in #11040–#11042 are a 120-second working window, a 10-minute hung-tool threshold extended by a longer explicit wait, five identical completed calls with token growth across five minutes and no worktree change for looping, and two confirmed missing-runtime probes at least 15 seconds apart for crashed. `TAILTERM_ACTIVITY_WORKING_SECONDS`, `TAILTERM_ACTIVITY_HUNG_SECONDS`, `TAILTERM_ACTIVITY_LOOP_SECONDS`, `TAILTERM_ACTIVITY_LOOP_CALLS`, and `TAILTERM_ACTIVITY_CRASH_PROBE_SECONDS` override those bounds. Probe errors and unknown transcript formats yield `unknown`. Planned `needs_input` waits do not trigger hung or crash classification. Detection only notifies; it never nudges, resumes, interrupts or restarts an agent.

The relay polls activity after inbox and broker delivery and uses the existing host request budget. It saves a pending transition and stable request identity before HTTP; a lost reply replays the same report no more than once per 15 seconds. The hub stores one snapshot per exact agent run and an immutable retry receipt. A steady state, including token growth, creates no hub write. Agent and team usage are last-transition snapshots, not live counters. Team totals are derived from persisted exact-run snapshots linked to the work item, including closed runs. A shared worktree fingerprint can show change, but cannot identify which agent edited it.

Projects shows the activity state beside lifecycle and the last-transition usage and evidence age in agent details. `tt agents` shows activity plus the same usage snapshot. Delivery and `tt team queue list` show each member's state and team totals. On a transition to `hung_tool`, `crashed` or `looping`, the hub sends one typed notice to that item's current lead. A crash also posts an owner-facing notice; a lead's hung-tool or looping transition posts one owner-facing notice. No team outside the item's own lead mapping receives a directed alert.

Synthetic checks are `go test ./cmd/tt -run TestActivity`, `go test ./internal/store -run TestActivity`, `node tests/activity-browser.mjs`, `go vet ./...`, `go test ./...`, and `npm test`. Browser checks use disposable Chromium and WebKit contexts; Go checks use synthetic transcripts, fake process/tmux probes and isolated SQLite/HTTP fixtures. No check reads a real agent transcript or touches the live hub or relay.
