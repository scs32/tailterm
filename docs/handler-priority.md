# Handler priority for live teams

Work item `wi_7149909a1085b653` revision 1, order #10414, owner choice #10802 and exact builder Start #10815 govern this change. The owner chose one database handler with priority for live-team gate requests. This implementation does not change inbox sequence, add a handler, or interrupt an in-progress database transaction.

The hub derives a handler request from a typed `REQUEST` addressed to the database handler when its stored sender run matches an admitted agent work-item binding and the message has a matching native primary item link. A request is currently high priority when that item's exact bound team has a member in `running`, `done` or `needs_input`. Retired, closed and exited members do not make a team live. Heartbeat age is not consulted. The request identity remains visible after the team closes; current priority is recomputed on each read.

`tt obligations` lists the handler's open live requests first, then all other obligations; each group keeps message sequence order. The broker wake prompt applies the same ordering before choosing its first five entries, so a late live gate is not hidden behind older queued work. Other agents' obligation lists and every inbox cursor remain in sequence order.

The database handler prompt requires a fresh `tt obligations` check before each new queued-item record. It acknowledges and answers live Start, plan and assignment gates with a typed `RESULT --reply-to`, then checks again before the next queued record. It finishes any already-started atomic record safely. When live gates drain, queued intake proceeds. This is a prompt contract rather than preemption or a wall-time guarantee. Running threads and previously frozen launch plans are not rewritten by the prompt update.

The obligation API adds `handlerRequest`, `handlerPriority`, `pendingAgeMillis` and `responseMillis`. Pending age is request creation to read time. Response duration is request creation to a typed result or decline, retaining request and outcome sequence IDs. `tt obligations` shows these values per handler request; `tt message-checks --summary` shows pending count, blocked count, oldest age, completed count, median, max and the slowest request/outcome pair. Cancellation and withdrawal are reported separately and never counted as successful responses. Inbox reads, delivery, acknowledgement, progress and agent turn or closeout events are not response outcomes. Existing `tt message-checks --json` output is unchanged.

The isolated fake-clock store tests replay a live lead, planner and builder beside a queued-only item and one fake handler. They cover a live gate arriving after more than fifty older entries, wake first-five visibility, a recheck between queued writes, eventual queued drain, wrong-run and unrelated or unbound requests, and unchanged inbox and non-handler order. The focused Go and JS commands are in the assignment plan #10797; all tests use temporary databases and no live task or handler.
